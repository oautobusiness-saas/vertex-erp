0. الهوية المعمارية العامة
Local-First Multi-Tenant Architecture with Isolated Client Data
•	Local-First: بيانات كل عميل التشغيلية تعيش فيزيائيًا على أجهزته فقط، لا تُرسل لأي خادم أبدًا.
•	Multi-Tenant: نظام واحد يخدم عددًا غير محدود من العملاء والتخصصات؛ إضافة أي تخصص جديد = إضافة مستقلة لا تمس أي عميل أو تخصص قائم (Bounded Contexts).
•	Tenant Isolation فيزيائي؛ Module Isolation منطقي.
•	دعم تعدد المحاسبين/الأجهزة من الأساس: خادم PostgreSQL محلي خفيف على جهاز "رئيسي" داخل شبكة المنشأة (LAN) فقط، لا يوجد أي اتصال سحابي لهذه الطبقة. باقي الأجهزة تتصل به عبر الشبكة الداخلية. هذا نطاق صغير (عدد أجهزة محدود داخل منشأة واحدة)، وليس نظامًا موزَّعًا بمعايير مؤسسية ضخمة (لا Redis، لا Load Balancing، لا Replication معقدة — غير منطقي لحجم العميل المستهدف).

1. البنية العامة وفصل طبقتي البيانات
•	برنامج مكتبي واحد (كود موحّد)، أوفلاين على ويندوز.
•	ملف إعدادات مشفَّر لكل عميل (Tenant Config): نشاطه، تسمياته، الوحدات المفعَّلة له فقط.
•	الطبقة الإدارية المركزية (Supabase) — الحد الأدنى الضروري فقط: 
o	حالة الترخيص (نشط/منتهٍ) — تُتحقَّق أساسًا عبر Lemon Squeezy مباشرة، وليس بيانات إضافية نخزّنها نحن.
o	سجل الإحالات ورصيد الكوينز (موضّح في القسم 12).
o	الرسائل التي يختار العميل إرسالها بنفسه.
o	تم إزالة "عدد الفواتير" نهائيًا من أي بيانات تُرسل — لا داعٍ له، وكان يسبب قلقًا غير ضروري للعميل بدون فائدة تستحق الإفصاح عنه.
•	بند الموافقة الأساسي: العميل يوافق صراحة على شروط الاستخدام، ويكون هو المسؤول الكامل عن صحة كل البيانات وشكل استخدامه للبرنامج.
•	الاستخدام الدولي: عملة/ضريبة/تاريخ قابلة للتخصيص؛ وحدة امتثال ضريبي اختيارية حسب دولة العميل.

2. قواعد العمارة الإلزامية (Bounded Contexts)
المبدأ	التفاصيل
Core Domain	Identity, Tenancy, Users/Roles/Permissions, Customers, Suppliers, Products, Warehouses, Sales, Purchases, Payments, Cash & Banks, Accounting (قيد مزدوج كامل), Tax, Invoicing, Audit, Files, Notifications, Configuration
Bounded Contexts	كل تخصص مستقل: لا استيراد كود، لا قراءة جداول مباشرة، لا Cross-Module FKs/SQL
Integration	داخل العملية الواحدة (In-Process Synchronous Mediator): الحدث يُنشر ويُستهلك داخل نفس المعاملة الذرية (DB Transaction) — يحافظ على عزل الاعتماديات البرمجية مع ضمان الذرّية والفورية
Dependency Direction	Industry Module ← Stable Core Contracts ← Core Domain ← Infrastructure
Plugin Architecture	كل تخصص: Install/Enable/Disable/Upgrade/Remove مستقل
Backward Compatibility	ممنوع حذف/تسمية حقول دون خطة ترحيل + طبقة توافق
No Hidden Coupling	ممنوع متغيرات عامة، حالة مشتركة، اعتمادية دائرية
Concurrency (متعدد الأجهزة)	قفل تفاؤلي بسيط (Optimistic Locking) بختم إصدار (Version Stamp) لكل صف — لو جهازان عدّلا نفس الفاتورة، الثاني يُنبَّه "تم التعديل من جهاز آخر، حدِّث الصفحة" بدل الكتابة فوق بصمت
خطة إلزامية: Core + إطار الوحدات أولًا، ثم تخصصان تجريبيان (Dummy) لإثبات العزل الكامل، قبل أي تخصص حقيقي.

5. المحاسبة — قيد مزدوج كامل (Double-Entry) من الأساس
قرار نهائي معتمد: كل حركة مالية في النظام (بيع، شراء، تحصيل، دفع، مصروف، حركة موظف، حركة بنكية) تُسجَّل كقيد محاسبي كامل: حساب مدين + حساب دائن، بقيمة متساوية دائمًا، ولا يُقبل أي قيد لا يتوازن فيه إجمالي المدين مع إجمالي الدائن.
العنصر	التفاصيل
دليل الحسابات (Chart of Accounts)	هيكل أساسي جاهز مسبقًا (أصول، خصوم، حقوق ملكية، إيرادات، مصروفات) قابل للتخصيص الطفيف لكل تخصص
كل حركة في اليومية	تُنتج قيدًا واحدًا أو أكثر تلقائيًا خلف الكواجهة — المستخدم لا يرى "مدين/دائن" في واجهة الفاتورة العادية، الواجهة تبقى بسيطة كما صُممت (القسم 6)، لكن المحرك الداخلي يُسجِّل قيدًا مزدوجًا كاملًا في كل مرة
التقارير المالية	ميزان مراجعة حقيقي، قائمة دخل، قائمة مركز مالي — كلها تُشتق مباشرة من القيود دون حسابات تقريبية
قابلية التوسع	يفتح الباب لاحقًا لتقارير معيارية (IFRS/GAAP) ولتعدد العملات والفروع دون أي إعادة هيكلة لاحقة
ملاحظة تنفيذية: الواجهة الأمامية (Frontend) تبقى بسيطة تمامًا للمستخدم النهائي كما صُمِّمت بالكامل في القسم 6 — التعقيد المحاسبي محصور بالكامل في محرك الخلفية (Accounting Core Engine)، ولا يظهر للمحاسب أو المالك أي مصطلح "مدين/دائن" في شاشاته اليومية.

6. دفتر اليومية وشاشة الفاتورة (تجربة المستخدم — بلا تغيير عن التصميم المبسّط)
6.1 اليومية
•	رقم مسلسل دائم، تاريخ ووقت تلقائي، نوع الحركة، الطرف، البيان، القيمة، طريقة الدفع.
•	الأكواد ثنائية الاتجاه لكل كيان. لا حدود عددية.
•	آلية الربط الفوري: اختيار "بيع" يفتح شاشة الفاتورة مباشرة.
6.2 شاشة الفاتورة
•	كود العميل يستدعي الاسم + المديونية القديمة فورًا. كود الصنف يستدعي الاسم/الوحدة/السعر.
•	سعر الوحدة قابل للتعديل لهذه الفاتورة فقط.
•	ترتيب الحساب: إجمالي الفاتورة ← + المديونية القديمة ← = المستحق الكلي ← − المدفوع ← = المتبقي.
•	الدفع المقسّم (كاش+تحويل) مدعوم.
•	المرتجعات: رسمي (موافقة يدوية + تأكيد نجاح + إرجاع للمخزون) منفصل عن التسوية المباشرة (خصم حساب فقط).
6.3 حسابات العملاء والموظفين والمصروفات
•	الحد الائتماني ومدة السماح: يحددهما المالك لكل عميل؛ تنبيه شهري بالمدينين الخاملين.
•	الموظفون: أجرة يومية + دورة قبض (أسبوعية/شهرية)، صافي مستحق تلقائي.
•	المصروفات: خانة ثابتة في اليومية، وصف حر، تُخصم من رصيد الدرج تلقائيًا.

8. الأمان — ❗ والصلاحيات
8.1 شاشة الدخول — حسابات مستقلة لكل مستخدم
•	شاشة الدخول تعرض خانة باسوورد فقط (بلا اسم مستخدم ظاهر)، بنفس فلسفة شاشة قفل ويندوز.
•	حساب مستقل لكل محاسب (اسم مستخدم + باسوورد خاص به)، وليس باسوورد محاسب مشترك — لضمان دقة سجل التدقيق (من فعل ماذا بالضبط).
•	حساب المالك منفصل بصلاحيات كاملة.
•	باسوورد صحيح (مالك أو محاسب) → يفتح البرنامج الحقيقي فورًا حسب صلاحيات الحساب.
•	الضغط على Enter مرتين متتاليتين بدون كتابة أي باسوورد → تفتح مباشرة لعبة خفيفة (بدون أي بيانات حقيقية أو وهمية على الإطلاق).
8.2 علامة ❗ أثناء الاستخدام
الجانب	الآلية
الموقع	علامة ❗ ثابتة داخل أي حساب مفتوح (مالك أو محاسب)
التفعيل	دبل كليك على ❗ يفتح فورًا نفس اللعبة الخفيفة (بلا أي بيانات من البرنامج)
عدد الألعاب	لعبتان خفيفتان في المرحلة الأولى (مثل كوتشينة ودومينو أو إكس أو)، بمظهر عصري بسيط، تحميل عند الفتح فقط (Lazy Loading) بدون أي أثر على أداء البرنامج أو الويندوز
البيانات	لا يوجد أي اتصال بقاعدة بيانات البرنامج من داخل اللعبة إطلاقًا — لا حسابات حقيقية ولا وهمية
الرجوع	لا يوجد زر رجوع من داخل اللعبة إلى أي حساب (مالك أو محاسب) إطلاقًا مهما كان الحساب الذي فتحها
الخروج الوحيد	إغلاق البرنامج بالكامل، ثم إعادة فتحه وإدخال باسوورد المحاسب أو المالك الصحيح ليعمل البرنامج بصورة طبيعية من جديد
الغرض	خصوصية وحماية من العبث أثناء ترك الجهاز مفتوحًا فقط — بدون أي محتوى مالي حقيقي أو وهمي يظهر لأي شخص غير مصرَّح له
8.3 (محجوز — لا حاجة لبند قانوني هنا لأن الميزة لا تعرض أي بيانات مالية حقيقية أو وهمية)
8.4 سجل التدقيق
•	كل تعديل بعد الحفظ يتطلب باسوورد المالك ويُسجَّل باسم المحاسب الفعلي (بفضل الحسابات المستقلة)، بما في ذلك توقيت تفعيل ❗ لكل جهاز.
8.5 كود دخول الطوارئ للمالك
•	وقت تسجيل أي عميل، يُلتقط معرف جهازه أوتوماتيكيًا للسجل المركزي. خانة بحث موحَّدة (اسم/إيميل/تليفون) + زر "توليد كود طوارئ" فوري. الكود يُرسَل للعميل عبر أي قناة، يُدخَل من خانة مخفية بشاشة الدخول ويفتح وضع المالك مباشرة.
•	بديل: AnyDesk/TeamViewer (أداة خارجية منفصلة تمامًا) للمشاكل الأعقد.
8.6 استرجاع كلمة السر
•	رمز عشوائي 6 أرقام، صلاحية 10 دقائق، يُرسَل على كل قناة مربوطة فعليًا (إيميل + تيليجرام مجانًا، SMS/واتساب مدفوع).

9. النموذج التجاري والترخيص (عبر Lemon Squeezy)
9.1 الآلية الأساسية
الخطوة	التفاصيل
التفعيل الأول	البرنامج يبعت معرف الجهاز لـ Lemon Squeezy API فيسجَّل كـ Instance مرتبط بالمفتاح
التخزين المحلي	حالة الترخيص تُخزَّن محليًا مشفَّرة "صالح لحد تاريخ X" (30 يوم افتراضيًا)، تُجدَّد كل مرة الإنترنت متوفر
الفحص	محلي بالكامل، لا يحتاج إنترنت دائم
الويبهوك	يصل لخادم خلفي (Supabase Edge Function)، يتحقق من التوقيع، يحدّث حالة العميل — لا يصل لجهاز العميل مباشرة
نقل الترخيص لجهاز جديد	إلغاء تفعيل الـ Instance القديم من لوحة Lemon Squeezy، تفعيل الجديد — بدون كود مخصص منا
9.2 الاشتراك الشهري
الجانب	الآلية

12. نظام الإحالات والكوينز + صفحة العميل الكاملة في لوحة تحكم المالك
12.1 آلية الإحالة والكوينز
الخطوة	الآلية
1-2	لينك إحالة فريد لكل عميل → عميل جديد يفتح به → "محتمل"
3-4	عند الدفع الفعلي الأول → 2000 كوين للمحيل + إشعار مزدوج (للمحيل ولمالك المنتج)
5	رصيد الكوينز حساب حر بالكامل (موجب أو سالب) — يمثّل مديونية العميل للبرنامج أو حقه لديه، بحرية تعديل كاملة من المالك
6	التجديد التلقائي الاستباقي: قبل انتهاء الاشتراك بـ3 أيام، فحص صامت للرصيد؛ لو كافٍ (≥2000)، خصم فوري وتوليد كود خصم Lemon Squeezy تلقائيًا وتفعيل الاشتراك دون أي طلب من العميل — يمنع الوصول لحظة القفل وعنده رصيد كافٍ

•	باب الإحالات والمكافآت: سجل كامل لكل إحالة فعلية قام بها هذا العميل تحديدًا — تاريخ كل إحالة، اسم المُحال، إيميله، تليفونه، وهل تحولت لعميل فعلي دافع أم لا تزال "محتملة".
•	سجل حركة الكوينز: كل عملية زيادة/نقصان (تلقائية أو يدوية)، تاريخها، سببها، والرصيد بعدها — بنفس منطق سجل مديونية العميل التجاري تمامًا.

17. قرارات مؤكدة نهائية (لا حاجة لإعادة سؤالها)
•	العمارة: Local-First Multi-Tenant، عزل فيزيائي + منطقي، حجم صغير-متوسط وليس مؤسسيًا ضخمًا.
•	المحاسبة: قيد مزدوج كامل من الأساس، بواجهة مستخدم بسيطة تخفي التعقيد.
•	حسابات المحاسبين: مستقلة لكل محاسب من الآن.
•	البيانات الإدارية المركزية: حد أدنى (بدون عدد فواتير)، موافقة العميل إلزامية ومسؤوليته الكاملة عن الاستخدام.
•	الترخيص والدفع: Lemon Squeezy بالكامل (تلقائي + يدوي بنفس الآلية).
•	الكوينز: حساب حر موجب/سالب، تجديد تلقائي استباقي + يدوي.
•	❗: يفتح لعبة خفيفة فقط بدون أي بيانات حقيقية أو وهمية، بدون زر رجوع من اللعبة، الخروج فقط بإغلاق البرنامج وإعادة فتحه بباسوورد صحيح.
•	صفحة العميل في لوحة تحكم المالك: بيانات كاملة + سجل إحالات + سجل كوينز.
•	إضافة أي عدد من التخصصات مستقبلًا آمنة تمامًا.

19. خطوات البدء الفعلي في البناء (بالترتيب، بدون أي تخمين)
1.	إنشاء مستودع GitHub باسم المشروع، ورفع هذا الملف كأول ملف فيه (مرجع دائم).
2.	إنشاء هيكل المجلدات المعماري: /architecture/adr, /contracts, /module-boundaries, /database, /security.
3.	توثيق أول 5 قرارات معمارية (ADR) كملفات Markdown منفصلة: Local-First Multi-Tenant، SQLite/PostgreSQL المزدوج، C#‎ عبر نموذج Python أولي، القيد المزدوج الكامل، Lemon Squeezy للترخيص.
4.	كتابة مخطط البيانات الأساسي (ERD نصي): جداول Core (عميل، صنف، يومية، قيد محاسبي، مستخدم، جلسة) بحقولها وعلاقاتها — هذه أهم خطوة قبل أي كود.
5.	فتح Codespace وبناء هيكل Core + أول تخصص ("تجارة عامة") بلغة Python، مع محرك القيد المزدوج من أول سطر.
6.	اختبار دورة كاملة يدويًا (شراء → بيع → تحصيل) والتأكد من توازن كل قيد محاسبي تلقائيًا.
7.	بناء تخصص تجريبي ثانٍ بسيط جدًا لإثبات العزل الكامل بين الوحدات قبل أي توسّع حقيقي.
8.	لا ننتقل لأي بند آخر (أمان، ترخيص، علامة ❗، تخصصات إضافية) إلا بعد نجاح الخطوات 1-7 فعليًا مع بيانات حقيقية.
